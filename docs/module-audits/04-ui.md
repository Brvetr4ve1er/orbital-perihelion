# UI Module Audit

Scope:

- `src/ui/App.tsx`
- `src/ui/components/*`
- `src/ui/features/dashboard/*`
- `src/ui/features/settings/*`

## Responsibility

The UI module is the operational face of the application:

- import entrypoints
- command palette
- dashboard views
- modal inspection and editing
- settings and backup surfaces
- product cards and comparison flows

## What Is Solid

- The app shell is readable and has a sensible import-to-dashboard progression.
- The dashboard is modular enough that one failing panel can be isolated by `ErrorBoundary`.
- The product card and dashboard composition show deliberate performance awareness.
- Lazy loading of heavier views is a good tradeoff.

## Verified Issues

### 1. UI exposes more capability than the underlying runtime guarantees

Examples:

- settings toggles for inactive runtime options
- backup import that requires reload
- manual AI enrichment path that is less correct than the queue path

Why this matters:

- The UI currently teaches the wrong mental model in some places.
- Operator trust is damaged more by false controls than by missing controls.

### 2. `ProductCard` comparator is narrow

Observed behavior:

- the memo comparator checks id, compare selection, `lastUpdated`, enriched presence, and retail price

Risk:

- UI changes triggered by other fields may not rerender if they do not also bump the watched fields as expected.
- The comparator is clever enough to be a future bug source.

Upgrade:

- Either make the product read model smaller and more explicit, or make the comparator compare a dedicated view hash.

### 3. The modal and queue represent two operational enrichment stories

The UI lets users enrich one product manually and also enrich all products through the queue. Because the write paths differ, the UI itself becomes a source of data inconsistency.

### 4. Settings and backup UX disclose limitations weakly

Observed behavior:

- backup import tells the user to reload
- secrets are scrubbed from settings persistence
- inactive settings are still interactive

The UI should explain these constraints before, not after, the action.

## Likely Hidden Risks

### 1. Dashboard density risk

The dashboard now aggregates many widgets and views. Even if each view is individually reasonable, the composition can become hard to maintain because every product mutation potentially has many downstream UI implications.

### 2. Mixed localization risk

The UI contains French-forward text, English code semantics, and some locale configurability. Without a deliberate localization strategy, string drift and inconsistent tone will continue.

### 3. CRUD integrity risk

The product modal contains editing flow hooks. As editing expands, the UI will need clearer validation, conflict handling, and mutation feedback than it has today.

## Upgrade Directions

### Medium-weight upgrades

- Add “inactive” labels or disable controls that are not wired.
- Route all AI actions through one enrichment command path.
- Add a diagnostics drawer for persistence failures, queue errors, and sidecar status.
- Consolidate product view rendering around a prepared read model instead of ad hoc field access.

### Heavy upgrades

- Introduce a workspace model:
  catalog state,
  sales state,
  enrichment jobs,
  diagnostics,
  backups,
  settings health.
- Add an import wizard and a guided AI-enrichment workflow instead of scattering those controls across header, modal, and settings.
- Separate operator mode from analyst mode:
  one for ingest/edit/configure, one for browse/analyze/compare.

## Recommended Priority

1. Remove misleading controls or mark them inactive.
2. Unify manual and queued enrichment UX.
3. Add a clearer diagnostics surface.
